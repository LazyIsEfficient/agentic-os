# Security Policy

## Why this file exists

Most of this library is **passive**: skills, agents, commands, and rules are Markdown — instructions a *model* reads. The worst case for a bad instruction is bad advice, with a human and the model in the loop.

Some skills also ship **helper scripts** (`.claude/skills/*/scripts/*.py`, `*.sh`) — real executable code, not Markdown. Unlike hooks, these run **only when a user or agent explicitly invokes them**; they are never registered to fire on their own. That user-in-the-loop trust model is why they are not the primary concern here — but they are still third-party code you are choosing to run, so audit a skill's `scripts/` before executing it, exactly as you would any downloaded tool.

**Hooks are different. They are executable code that the library distributes and that runs automatically on consumer machines — with no invocation and no tool call.** The Claude installers ship the full `.claude/hooks/*.sh` directory; `install.sh --codex` allowlists the compatible subset into the Codex hook directory. Once registered and trusted, a hook fires on routine events (e.g. `PreToolUse` on tool or shell activity, `SessionStart` on session open), runs with the user's full shell and permissions, and has **no sandbox**. This is the library's distributed executable surface, so it is the primary security concern.

## Threat model — the supply chain

The risk travels through the **distribution channel**. People install this library on trust; they do not audit every line of every shipped hook. That means:

- A **bug** in a shipped hook runs on everyone who installed it — not just the author.
- An **upstream compromise** (a malicious PR merged, or a maintainer account/CI compromised) propagates arbitrary code to every downstream installer automatically. One poisoned commit → code execution on N machines. This is the classic supply-chain attack shape (`event-stream`, `xz`).

Claude relies on the **workspace-trust gate** before project hooks run. Codex additionally requires review and trust of each non-managed hook definition (and requires project trust for project-local hooks). These are execution gates, **not** sandboxes.

### What ships today

**Claude Code (`install.sh` / `install.ps1`)**
- Ships `.claude/hooks/*.sh` and marks them executable.
- **Registers hooks globally** by merging `assets/consumer/claude-settings.json` into `~/.claude/settings.json`. At install time, template paths (`$HOME/.claude/hooks/…`) are rewritten to match the actual install `DEST`, canonicalised to an absolute path with no trailing slash (supports custom `CLAUDE_DIR`). Only the `hooks` block is merged; other top-level keys are preserved, and so is the file's mode (a `0600` settings file holding `env` secrets stays `0600`). The merge is **per event**. A hook handler counts as AgenticOS-owned **only when its whole `command` (whitespace-trimmed) exactly equals a template command**, in either the literal `$HOME/.claude/hooks/…` form or the form with the install hooks dir substituted. A compound or piped command that merely contains an AgenticOS hook path (`bash ~/.claude/hooks/block-bad-bash.sh; bash /opt/audit.sh`, `… | tee log`) is yours and is never touched; ours is appended beside it. In each event AgenticOS ships, install strips owned handlers (dropping matcher groups that become empty) and appends the template's groups. Your own hooks, including events AgenticOS doesn't ship and handlers you added inside an AgenticOS group, are preserved. Re-install is idempotent. A `settings.json` whose `hooks` is not an object, or whose value for a shipped event is not an array, fails the install closed and is left unmodified. Hooks a past release retired (`RETIRED_HOOKS` in `install.sh`, `$RetiredHooks` in `install.ps1`) are recognised the same way and stripped from **every** event on install. `--uninstall` / `-Uninstall` strips template and retired handlers from every event, drops only the groups and events that this empties, and leaves everything else, including your hooks, in place.
- **Shipped hook files are always refreshed.** Re-running the installer replaces every AgenticOS hook script with the release copy, so a security fix to a hook reaches existing installs without `--force`. If the on-disk copy differs, it is first saved as `<file>.bak.<timestamp>` and the installer warns. Other files are tracked in `.agentic-os-manifest.json` (path + SHA-256 per file): an unmodified file is updated, a modified one is kept and named, a file the release dropped is pruned if unmodified, and files not in the manifest are never touched. Every write, backup, and delete goes through one path gate (`safe_rel` in `install.sh`, `Test-SafeRel` in `install.ps1`). The gate requires every path component to be `[A-Za-z0-9._@+-]` with no `.` or `..`, and requires at least two components, the first of which is a shipped directory (`skills`, `agents`, `commands`, `hooks`; Codex: a skill dir, `agents`, `hooks`). A skills path must name a skill that AgenticOS ships, has shipped (`assets/release-hashes.txt`), or has tombstoned, so a tampered manifest cannot reach another tool's skills in a shared `~/.agents/skills`. No component from the install root to the file may be a symlink or a Windows reparse point. That includes a dangling link at the leaf. The parent must also resolve inside the root: `pwd -P` against the canonical root on bash, and a normalised full-path prefix in ps1. Anything that fails the gate is reported and left alone. Every write is made through a fresh, uniquely named temp file in the same directory and then `mv`d over the target. A link planted at a predictable `.tmp` name therefore never redirects it, and a hard-linked file gets a new inode, which leaves the other links untouched. The installer reports a hard-linked hook. A symlinked manifest, `settings.json` or `hooks.json` is refused with nothing changed, rather than written through. That rules out a tampered or repo-controlled manifest (`--codex --project`) naming `settings.json`, `CLAUDE.md`, or `../x`. It also rules out a skill dir symlinked elsewhere, and a legacy file name carrying a newline. The gate is re-checked immediately before each delete, and removal lists are NUL-delimited. Hook backups are named `<file>.bak.<timestamp>.<pid>`, with a counter if that name already exists. Before copying anything, the installer checks that `settings.json` / `hooks.json` will merge by running the real merge on a scratch copy, so a bad file fails with nothing changed. The installer also refuses to run, before writing anything, when the hook library it sources from the payload is older than the installer (`AGENTIC_OS_HOOK_LIB_API`, plus `declare -F` for each function it calls). That stops a new `install.sh` over an older release tarball from falling back to the old library's behaviour. A shipped top-level directory (`skills/`, `agents/`, `commands/`, `hooks/`) that is itself a symlink is refused with one error. Hooks are registered only after every shipped hook is verified on disk as a regular file at the release SHA. If any is missing, nothing is registered, the manifest is left as it was, and the run exits non-zero. On uninstall the hook registrations are removed **before** any file, so a failed `settings.json` rewrite never leaves a registered command pointing at a deleted script.

**Codex (`install.sh --codex`)**
- Ships only `session-state-inject.sh` and `session-state-checkpoint.sh` to the user or project Codex hook directory and marks them executable.
- Registers `assets/consumer/codex-hooks.json` in `~/.codex/hooks.json` (user scope) or `.codex/hooks.json` (project scope). Re-install replaces only matcher groups marked `AgenticOS:`, in every event, and preserves unrelated hook groups. `--codex --uninstall` removes only the `AgenticOS:` groups. Hook files and manifests follow the same rules as Claude.
- Hooks remain inert until the user reviews and trusts them with `/hooks`. Project hooks also require a trusted project.

**Shipped hook scripts (active after install):**
  - **Ergonomics, not security:** `block-bad-bash.sh` — a `jq`-gated nudge, explicitly self-labeled *not a security control*. Blocks long `&&` chains and `cd && git` patterns (exit 2).
  - **Policy (fails closed):** `block-general-purpose.sh` is a PreToolUse hook on `Agent|Task`. Installing it bans `general-purpose` and untyped subagent spawns in every consumer project, because the dispatch doctrine requires named specialists and an omitted `subagent_type` silently falls back to the catch-all agent. It emits `permissionDecision: "deny"`. Failures inside the script fail closed: a missing jq or an unparseable payload also denies. A hook that can't start or times out is a non-blocking error unless its entry sets `"onFailure": "block"` (Claude Code v2.1.295+). This repo's `.claude/settings.json` sets that key. It has no bypass switch.
  - **Post-edit scan (fails open):** `post-edit-scan.sh` is a PostToolUse hook on `Edit|Write|MultiEdit`. It checks only the file just edited. The file must resolve (symlinks followed) inside the project root, be at most 1 MB, and have a path with no control characters. A newline in a path could forge lines in the model-facing reason, so such files are skipped. It looks for committed-looking secrets with a built-in regex set plus `gitleaks` when installed. gitleaks runs with `--redact`, ignores the repo's `.gitleaksignore` and `gitleaks:allow`, has `GITLEAKS_CONFIG*` unset, and is killed after 5 s. The hook also does fast syntax checks (`bash -n`, `jq empty`, `python3` py_compile with bytecode in a temp dir). Findings go back to the model as `decision: "block"` + `reason`, reported as `file:line rule` with the secret value never printed. Syntax findings report only the line number and error class, because checker messages can quote the source. Output is capped at 20 findings. It has no network access and runs no project linters. It fails open (missing jq, malformed payload, scanner error or timeout → one stderr line, exit 0) because a PostToolUse hook runs after the write and cannot undo it.
  - **Review gate (Tier 0, fails open):** `review-verdict-capture.sh` (SubagentStop) and `review-gate-stop.sh` (Stop), with the shipped parser `lib/parse-verdict.sh` (#258). Capture acts only on the exact agent types `code-reviewer`, `security-reviewer`, `library-reviewer`, `data-model-verifier`. It parses the subagent's `last_assistant_message` (or the last assistant entry of `agent_transcript_path`, only when it resolves under `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/`, reading at most 1 MiB). The git root comes from the payload `cwd`, falling back to `CLAUDE_PROJECT_DIR`. Capture writes only `<git-root>/.claude/reviews/<HEAD-sha>-<agent>.json` and `.claude/reviews/.gitignore`. Each is written as a `mktemp` file in the same directory and then `mv`'d into place.
    - It refuses when `.claude`, `.claude/reviews` or that `.gitignore` is a symlink, including a dangling one a repo can commit, or when `.claude/reviews` resolves outside the git root.
    - The filename is built only from the allowlisted agent name and a hex SHA from git, so reviewer text cannot steer the path.
    - Reviewer output is treated as untrusted data. It is only ever parsed by jq, never executed or injected into context.

    The Stop gate reads only those artifacts plus `git diff`/`ls-files` output, and blocks via `{"decision":"block"}`. It executes no project code, with one exception: the `scripts/gate-plan.sh` of the checkout the hook itself lives in, when that checkout is the same repository (same git common dir) as the tree under review. Consumer installs (`~/.claude/hooks`) use a built-in fallback rule instead, so a globally installed hook never runs a script from whichever repo it lands in. Both hooks **fail open** (missing jq/git, malformed payload, git or planner error → note, allow), so a broken gate cannot trap a session. The gate's note goes to stderr plus a `systemMessage`, once per session, via a marker in a private per-uid temp dir.

    **Limitation: a process gate, not an adversarial control.** It catches a session that *forgets* review. It does not stop one that is determined to skip it:
    - The artifacts are unauthenticated. Anything with repo write access, including the model's Bash tool, can write a `pass` file for HEAD.
    - The diff under review can edit `scripts/gate-plan.sh` to choose its own reviewers, or `.claude/agents/*-reviewer.md` to redefine what they check.
    - The base ref is whatever the local refs say. Moving `origin/HEAD` onto HEAD triggers a warning only when another candidate ref still shows HEAD ahead of it. The gate allows **with no warning** in three cases:
      - the repo has a single candidate ref and it is moved to HEAD;
      - every candidate ref (`origin/HEAD`, `origin/main`, `origin/master`, `main`, `master`) is moved to HEAD;
      - commits land directly on the default branch, so HEAD equals the base.

    The control for those cases remains human PR review, and CI once it checks artifacts. See the design on #258. Opt out with `AGENTIC_OS_REVIEW_GATE=off` in Claude Code's own environment (set at launch, or via a settings `env` entry). An `export` inside a Bash tool call runs in a child shell and does not reach hooks.
  - **Awareness harness:** `session-state-inject.sh`, `session-state-digest.sh`, `session-state-checkpoint.sh`, `survey-before-act.sh` — plain stdout. `SESSION-STATE.md` is governed by rule 7 below.
  - **Memory (write + read):** `memory-extract.sh` — the end-of-session Stop hook that nudges the `memory-extraction` skill — and `memory-inject.sh` — the SessionStart hook that surfaces the `.claude/memory/MEMORY.md` **index** so recorded facts re-enter context (#225). Both plain stdout. Both ship under `.claude/hooks/` but are **not** registered in the consumer `claude-settings.json` template, so they are inert on consumer installs (wired only in this repo's own `.claude/settings.json`). The `MEMORY.md` index `memory-inject.sh` injects is untrusted, user-local data governed by rule 7 below — gitignored, per-developer, and framed as DATA.

**To disable:** delete the `hooks` key from `~/.claude/settings.json`, or remove individual hook entries.
For Codex, disable the entries with `/hooks` or set `[features].hooks = false`.

## Policy for shipped hooks

Every hook that ships to consumers MUST:

1. **Live as a vendored `*.sh` shell script** under `.claude/hooks/`. Other interpreters evade the shell-idiom denylist and are rejected on file type. Hook `command` entries in any shipped hook config must *invoke* such a script — never carry inline shell:
   - `settings.json` — `<interpreter> .claude/hooks/<name>.sh [simple args]`
   - `codex-hooks.json` — `bash "$HOME/.codex/hooks/<name>.sh"`
2. **Make no runtime network call** — no `curl`/`wget`/`nc`/`scp`/`sftp`, no `/dev/tcp`, no pipe-to-shell (`… | bash`). Nothing is fetched or executed from the network at runtime.
3. **Contain no dynamic/obfuscated execution** — no `eval`, no `base64 -d | sh`, no `source <(…)`, no inline `python -c` / `node -e`.
4. **Touch no credentials, persistence, or privilege** — no `~/.ssh`/`~/.aws`/`~/.gnupg`/`id_rsa`/`.npmrc` access, no `crontab`/`launchctl`/`systemctl`/LaunchAgents, no `sudo`, no `chmod 777`, no recursive deletes of `$HOME`/`/`.
5. **Be minimal and auditable** — small enough to read in full in one sitting. Do not chase completeness pattern-by-pattern (see the note in `block-bad-bash.sh`).
6. **Pass human security review before merge** — a maintainer or `security-reviewer` pass is required for any new or changed shipped hook (the "ship + ratchet" review gate).
7. **Treat any file a hook injects into context as untrusted, user-local, never-committed data.** Hooks that read a file and emit it into the model's context (e.g. the `session-state-*` hooks emitting `SESSION-STATE.md`) create a standing prompt-injection channel: whoever can write that file controls text injected every session/turn with no tool call. So such files MUST stay gitignored and per-developer (never committed, never in a shared/multi-writer checkout), and the injected block MUST be framed as DATA, not instructions. `SESSION-STATE.md` is gitignored for exactly this reason.

## Enforcement — and its limits

`scripts/validate.sh` **Invariant 8 (`hook-safety`)** is a **defense-in-depth tripwire** for rules 1–4 — it is **NOT the safety boundary**, and nothing here should be read as "Invariant 8 makes shipping a hook safe." It runs in CI on every PR and push (`.github/workflows/validate.yml`); `scripts/validate-test.sh` pins each covered idiom as a Tier-0 regression. It has two halves applied to the hook surface:

- **(a) Denylist scan** of shipped hook *scripts* (`.claude/hooks/*.sh`).
- **(b) Strict-shape allowlist** for hook *command* entries in config JSON:
  - `settings.json`: exactly `<interpreter> .claude/hooks/<name>.sh [simple args]`
  - `codex-hooks.json`: exactly `bash "$HOME/.codex/hooks/<name>.sh"`

Anything else — a chained `; curl…|bash`, a literal-newline statement, an `env` prefix, a `../` path traversal, a `$(…)` subshell — fails the shape and is rejected. This is an allowlist of *shape*, not a denylist of metacharacters (which is incompletable — an early denylist version missed the newline separator), so a single vendored call cannot become a chain.

**This is a tripwire, not a sandbox, and the denylist half is fundamentally incompletable.** A static denylist of egress idioms cannot be finished by enumeration (resolver-based DNS exfil, variable-indirection, string-rebuild, and the next idiom nobody listed all evade it). So **the denylist catches the obvious and the accidental; it does not stop a determined attacker.** What actually makes a hook safe is the *layered* controls, of which the regex is the weakest: **(rule 5) minimal scripts a human reads in full + (rule 6) human security review of every shipped hook + (rule 2) the no-runtime-fetch policy + the workspace-trust gate.** The strict-shape half (b), by contrast, IS completable — it is an allowlist of command *shape*, not a denylist of idioms — and is the load-bearing deterministic check. **Active global hook registration (shipped since v2.3) is gated on human review of hook scripts + strict-shape templates; the egress denylist is never treated as complete.**

**Accepted, by-design limits of the regex denylist (NOT bugs — defended by the other layers):** the scan matches *literal* command idioms, so it cannot catch a payload assembled to defeat pattern-matching — most notably **variable indirection** (`A=cu; B=rl; "$A$B" http://…` reconstructs `curl` from fragments no single token matches), and equally string-reversal, `printf`-built command names, or an `IFS`/brace-expansion trick. Chasing these pattern-by-pattern is a losing game against a regex; they are out of scope for the tripwire and are caught instead by **rule 5 (minimal, auditable scripts a human reads in full)** and **rule 6 (human security review of every shipped hook)**. What the denylist *does* cover is the high-signal direct idioms — network tools (incl. `ssh`/`rsync`), version-suffixed and space-or-no-space `-m` interpreter invocations (python/node/perl/ruby), `openssl s_client`/`enc`, here-strings/heredocs and pipes fed to a shell, `eval`/`base64`/process-substitution — so an *accidental* or low-effort-malicious direct use trips the gate. `validate-test.sh` cases 11–26 pin the covered idioms as Tier-0 regressions. The covered set is "the idioms we've seen tried," not a closed enumeration — new direct idioms get added as they're found (the ratchet), but the layered defenses above, not the regex, are what make a hook safe.

## Shipping the awareness harness

The full Claude awareness harness (session-state hooks, survey-before-act, `/state` command, writer, skill) ships active by default. The Codex path registers only session-start injection and pre-compaction checkpointing; Codex requires explicit hook trust before they run.

**Consumer template** (`assets/consumer/`):
- `claude-settings.json` → `~/.claude/settings.json` (AgenticOS handlers merged per event with `DEST`-relative paths; your hooks and other top-level keys preserved; `--uninstall` removes only the AgenticOS handlers)
- `codex-hooks.json` → user or project `hooks.json` (AgenticOS matcher groups merged with destination-relative paths; unrelated groups preserved)

Invariant 8(b) validates this template. Human `security-reviewer` sign-off applies to hook script changes; the layered controls in Enforcement remain the real safety boundary — not the egress regex tripwire alone.

**To turn off:** run `./install.sh --uninstall` (removes only the AgenticOS entries), or remove individual entries from the `hooks` block in global settings. In Codex, use `/hooks` or disable the hooks feature.

**Writer note:** the skill-local writer is not scanned by Invariant 8 (hooks dirs only). It is benign by construction (bash/awk/coreutils; no network/exec/persistence/credentials).

## Reporting a vulnerability

Report privately via a **GitHub Security Advisory** on the repository (`LazyIsEfficient/agentic-os`) rather than a public issue. Please include the affected file(s), the execution path, and a proof-of-concept if you have one. Do not open a public issue for an unfixed vulnerability.
